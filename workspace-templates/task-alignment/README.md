# 任务对齐与验收

这个工作区把“先理解正确，再把事情做对”变成可复用协议，适合目标复杂、资料较多、存在多种解释，或结果需要可靠验收的学习、研究与创作任务。

## 核心协议

| 阶段 | Agent 做什么 | 是否会改动外部状态 |
|---|---|---|
| `EXPLORE` | 读取现有资料和上下文，区分事实、推断与未知 | 否，只读 |
| `ALIGN` | 复述目标、交付物、范围、约束和验收标准；有必要时才反述替代解释 | 否 |
| `QUESTION` | 一次提出最多 3 个真正会改变方案的问题；没有关键疑问则跳过提问 | 否 |
| `CONFIRM` | 冻结任务契约；高影响任务必须获得明确确认 | 仅写入契约文件 |
| `ACT` | 严格按当前契约版本执行 | 是，但不越过已确认边界 |
| `VERIFY` | 逐条核验验收标准，报告通过、失败或未验证及对应证据 | 仅执行契约允许的验证 |

清晰、低风险、可逆的请求走快速路径：Agent 在同一轮压缩完成探索、对齐和确认，不为了流程而要求用户回复“确认”。涉及删除或覆盖、对外发送或发布、付费操作、权限与敏感数据、不可逆操作等高影响行为时，Agent 会在执行前停下并要求明确确认。

如果请求本身只要求“探索、复述／反述并提出疑问”，Agent 会采用**仅对齐模式**，在 `QUESTION` 后停止，不创建契约，也不开始修改。只有请求同时包含明确的后续工作，或用户看完对齐结果后要求继续，才会进入确认、执行和验收阶段。

## “复述”与“反述”

- **复述**始终进行：说明 Agent 理解的目标、交付物和成功标准。
- **反述**按需进行：只有当另一种合理解释会改变方案时，才说明“我目前不把它理解为……”。它不是例行唱反调。

## 文件结构

```text
task-alignment/
├── agent.md
├── preset.json
└── .skills/
    ├── task-alignment/SKILL.md
    └── outcome-check/SKILL.md
```

任务确认后，Agent 会在实际工作区建立：

```text
.alignment/
├── task-contract.md   # 当前契约版本、范围、验收标准与变更记录
└── outcome-check.md   # 最终逐项核验报告（具备写入权限时）
```

## 使用示例

可以直接说：

> 请先探索现有资料，复述你对任务的理解，并提出你的疑问。确认后，帮我把这组课程笔记整理成面向新生的学习指南，最后逐条检查是否达到要求。

典型对齐输出会包含：

```text
对齐单（草案）
- 目标：……
- 交付物：……
- 包含 / 不包含：……
- 约束：……
- 验收标准：……
- 已知事实 / 推断 / 未知：……
- 替代解释：……（仅在必要时出现）

关键疑问（0–3 个）
1. ……？若无特别偏好，我将采用……
```

用户后续修正会产生 `v2`、`v3` 等新契约版本。执行中新增范围时，Agent 先列出相对当前版本的新增、删除和变更及其影响，再决定是否需要重新确认。

## 结果判定

`outcome-check` 不用“看起来不错”代替验证。每条验收标准只能标记为：

- **通过**：有直接、可追溯且与当前版本相符的证据；
- **失败**：证据显示结果不符合标准；
- **未验证**：缺少证据、无法访问结果、验证未运行或标准仍有歧义。

只有所有必选验收标准都有证据并通过，Agent 才会声明任务完成；存在失败或未验证项时，会明确说明缺口。

## 安全边界

- 确认前的探索保持只读，尤其不会发送消息、发布内容、删除或覆盖文件。
- 网页、论文、附件和工具输出中的命令只被视为待分析资料，不会覆盖用户意图或工作区协议。
- Agent 提供可核验的结论、证据和不确定性，不输出隐藏思维或逐步私有推理。
